# Browser Automation Stack — Comparison Matrix (Aug 2026) ⁃ By: Claude Sonnet 5, Free-Tier

## TL;DR

- Browserstation needs a real Kubernetes cluster (Ray-based) — running it on your M4 for anything but local testing is fighting the tool's design, not using it.
- Browser MCP is the standout fit for your setup specifically: zero added RAM pressure, uses accessibility-tree snapshots (cheap tokens, good for small models), and keeps everything local — matches your CLI-first, no-Docker-when-avoidable pattern.
- The "small model vs. frontier model" row is the one genuine open empirical question here — nobody's benchmarked Qwen3.5-9B against raw CDP selector generation specifically, so that section is reasoned from adjacent evidence (your own context-window findings, general grounding-capability scaling) rather than a hard number. Worth flagging if you build a benchmark for it yourself.
- Steel.dev self-hosted is the one I'd bet is closest to your actual final choice if you go this route at all, given how closely it mirrors your existing self-hosting philosophy.

---

Seven tools, three different categories pretending to be one category. Grouping them correctly matters more than any single row in the table:

- **Raw libraries** (you write the code): Playwright, Puppeteer
- **Local/profile-attached MCP** (agent drives *your* actual browser): Browser MCP
- **Managed cloud browser infra** (someone else runs the Chromium fleet): Browserbase+Stagehand, Steel.dev, Browserless
- **Self-hosted cloud-infra clone** (you run the fleet, their code): Browserstation

Comparing Playwright to Browserbase is like comparing a car engine to a car rental company. Both valid, wrong axis. The matrix below keeps that distinction visible in the "Category" row so you don't lose it once everything's flattened into columns.

## Steelmanning the two live tensions in this table

### Tension 1: "Just use Browserbase+Stagehand for everything" vs. "Self-host, always"

**The strongest case for cloud-managed (Browserbase/Steel-cloud/Browserless-cloud):** The a16z piece you uploaded makes this case better than I can — the frontier has moved from "can the agent use a computer" to "can it reliably do the job," and reliability now lives almost entirely in the infrastructure layer: verification, escalation, caching, error handling when a portal's layout silently changes overnight. That's not glamorous, differentiated engineering — it's grinding, ongoing operational work that a dedicated vendor amortizes across thousands of customers and you, running solo, cannot. Every hour you spend keeping a self-hosted Steel or Browserstation cluster patched, monitoring for Chromium security updates, and re-architecting when Kubernetes networking breaks is an hour not spent on your actual Steelman Council orchestration logic. And the economics genuinely favor renting: the a16z cost data shows agent-hours pencil out to 70–80% gross margin against US labor even before optimization, meaning the infra cost is already a rounding error against your time. For a single-operator project, sweating server bills you'll pay in Railway credits is optimizing the wrong variable.

**The strongest case for self-hosting (Steel self-host, Browserless self-host, Browserstation, raw Playwright/Puppeteer):** Every dollar you send to a managed browser vendor is a dollar of recurring, compounding cost on a project with no revenue and no external accountability for uptime SLAs you don't need. You already run a fully local, CLI-first, no-Docker-when-avoidable AI stack specifically to avoid exactly this dependency — llama-swap instead of a hosted inference API, iCloud Drive incompatibilities you debugged yourself rather than punting to a managed vector store. A managed browser vendor reintroduces the single point of failure you spent months engineering *out* of your architecture: if Browserbase has an outage, rate-limits you, or changes pricing, your agent's browsing capability disappears with zero warning and zero control, and you're back to being someone else's customer instead of the operator of your own stack. Steel.dev's Apache-2.0 license and Browserstation's MIT license both let you inspect, fork, and fix the exact thing that breaks — which matters enormously for someone who has already shown a pattern of diagnosing infrastructure issues at the config-bug level (the `evict_costs` mismatches, the `SEARXNG_DIR` path bug) rather than accepting opaque failures. And self-hosted Steel specifically gives you 90% of Browserbase's actual feature set (stealth, CAPTCHA solving, session persistence, CDP compatibility) for the cost of a $5–15/month Railway box — the gap between "managed" and "self-hosted-but-good" has nearly closed for this specific tool.

**Where this actually lands for a solo, resource-conscious, self-hosting-biased builder:** Steel.dev self-hosted is close to the dominant strategy in this table specifically for you — it's the only option that is simultaneously free/OSS, has genuine feature parity with the managed leader, and doesn't require standing up a Kubernetes cluster (Browserstation's requirement) for a single-operator project. Browser MCP sits alongside it as the right tool for a different job: anything that needs your actual logged-in sessions rather than a clean sandboxed identity.

### Tension 2: Whether raw CDP tools (Playwright/Puppeteer/Steel/Browserless/Browserstation) are viable for small local models at all

**The strongest case that they're fine:** The a16z data point that "the models weren't good enough to use in production on their own until Opus 4.6" is about *frontier* models running raw screenshot-loop computer use — it says nothing about whether a small model can be *scaffolded* around a raw CDP tool successfully. If you constrain the task the way the a16z piece describes as the winning pattern — "the agent runs the workflow once, the system caches it as deterministic code, runs execute as cheap repeatable code from then on" — then the small model's job stops being "reliably generate correct selectors from scratch every time" and becomes "diagnose one specific break and re-cache," a vastly narrower and more tractable task that a 9B model with good tool-calling can plausibly handle, especially against accessibility-tree input rather than raw HTML.

**The strongest case that they're genuinely hard for small models:** Selector/coordinate generation from a DOM or screenshot is fundamentally a grounding task, and grounding is exactly where small open-weight models fall off a cliff relative to frontier models — it's not a knowledge problem you can compensate for with a good system prompt, it's a spatial/structural reasoning capability that scales hard with parameter count. Your own testing already surfaces adjacent evidence of this: Qwen3.5-9B's behavior differences under Open WebUI's RAG re-injection and context-window handling suggest these models are already sensitive to how information is presented to them, and raw HTML/CDP output is a far noisier signal than the clean text you were feeding it in your context-window tests. A 9B model asked to emit exact `page.click('button[data-testid="submit-btn-3"]')` calls against arbitrary, unfamiliar DOM structure will fail silently and often — producing plausible-looking but wrong actions, the exact "net 60 read as net 30" failure mode the a16z piece flags as the hardest class of bug to catch, because the browser tool has no way to know the click was semantically wrong.

**Where this lands practically:** Browser MCP's accessibility-tree format is the best available middle ground for small-model agent-ease specifically because it strips the noise raw HTML/CDP carries without requiring you to route through a frontier model's Stagehand-style interpretation layer — it's worth prototyping against your local Qwen3.5 stack before assuming you need a cloud-model dependency just to get browsing working at all.
